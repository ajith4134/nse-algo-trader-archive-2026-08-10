## 1. Developer portal URL (app creation, api_key, redirect URL)
- Portal: **https://smartapi.angelbroking.com/** (aliased at
  `smartapi.angelone.in`; same product, Angel One rebrand). Sign in / sign up
  at `.../signin`. [A, official portal]
- Flow: **My Profile → "Create an App"** → pick API Type(s) (Publisher,
  Trading, Market Feed, **Historical Data**) → App Name, **Redirect URL**,
  Postback URL (optional), Angel Client ID (optional at this step) → Create
  App → portal issues **API Key** + **Secret Key**.
- **Redirect URL is a mandatory field on the form, but functionally inert for
  a client-code+PIN+TOTP script.** SmartAPI's programmatic login
  (`generateSession`) is a direct POST, not an OAuth redirect (see §3/§4) —
  the redirect URL only matters for the browser-based "Publisher"/one-click
  login flow. **Current policy (per SmartAPI forum moderator posts, topics
  4408 "Redirect URL" and 4849 "Issue with Localhost Redirect URL"): only
  HTTPS URLs are accepted — HTTP, localhost, and bare IPs are explicitly
  **no longer allowed**, a change from older guides (e.g. the angelone.in
  knowledge-center article "How to Generate SmartAPI Key..." which still
  says "use http://127.0.0.1" — that guidance is stale as of this policy
  change).** [B — forum moderator quotes via search snippets, not directly
  fetchable page; triangulated across two separate threads] Practical
  workaround for a personal script: any syntactically valid HTTPS URL you
  don't need to actually control (e.g. `https://www.google.com` or a GitHub
  Pages URL) satisfies the form; it is never hit during
  `generateSession`-based login.

## 2. What "client code" and "PIN/MPIN" are
- **Client code** = your Angel One **trading account ID / login ID** (the
  same ID you use to log into the Angel One trading app/web terminal). It is
  NOT generated by SmartAPI — it's your existing brokerage account number.
  Find it on the Angel One app/web login screen or account profile. Used as
  the `clientcode` parameter and the `username` argument to
  `generateSession()`. [A — corroborated by SDK source + knowledge-center]
- **PIN/MPIN** = the same 4-digit **MPIN** (or trading-terminal password) you
  use to log into the Angel One trading terminal — it is your account's
  login PIN, not a separate API-only secret. Passed as the `password`
  parameter to `generateSession()`. If TOTP/2FA hasn't been enabled yet on
  the account, it's set up separately at
  `smartapi.angelbroking.com/enable-totp` (client ID + MPIN + OTP to
  registered email/mobile) — but the user already has the TOTP secret, so
  this step is presumably done. [B]

## 3. Exact `generateSession` login flow
Confirmed directly from `SmartApi/smartConnect.py` in
`github.com/angel-one/smartapi-python` (primary source, GitHub — file read
in full):
- **Call:** `smartApi.generateSession(clientCode, password, totp)`
  - `clientCode` = client code (trading account ID)
  - `password` = PIN/MPIN
  - `totp` = `pyotp.TOTP(<your stored TOTP secret>).now()` (fresh 6-digit
    code, regenerated per call — the secret itself is never sent)
- **Transport:** POST to route `api.login` →
  `https://apiconnect.angelone.in/rest/auth/angelbroking/user/v1/loginByPassword`
  body `{"clientcode", "password", "totp"}`. This is a **direct credential
  POST, not an OAuth browser redirect.**
- **Response (`data['data']`):** `jwtToken`, `refreshToken`, `feedToken`.
  The SDK auto-sets these on the client instance and also fetches the user
  profile in the same call.
- **Historical data confirmed to use the jwtToken:** `getCandleData()` posts
  to route `api.candle.data` = the **"secure"** endpoint
  `/rest/secure/angelbroking/historical/v1/getCandleData` on the same
  `apiconnect.angelone.in` host — "secure" routes require the
  `Authorization: Bearer <jwtToken>` header the SDK attaches automatically
  after `generateSession`/`generateToken` sets it. [A — read directly from
  SDK source]
- Token refresh (no fresh PIN/TOTP needed until the daily cutoff, §6):
  `generateToken(refreshToken)` → POST `api.token` →
  `.../rest/auth/angelbroking/jwt/v1/generateTokens`, returns a new
  `jwtToken` + `feedToken`.

## 4. Redirect/callback URL for a local script
**Confirmed: SmartAPI login for a script is client-code + PIN/MPIN + TOTP via
a direct API POST — it does NOT use an OAuth redirect at all.** The Redirect
URL field is only required at **app-creation time** on the portal form (see
§1) and is only ever exercised by the separate browser-based "Publisher"
login button flow (where Angel One redirects a browser back to your app with
a token). For a headless historical-data-pulling script using
`generateSession(clientCode, pin, totp)` directly, the redirect URL is never
contacted — put any valid HTTPS placeholder in the form field and ignore it
thereafter.

## 5. Historical data intervals & no historical open interest
- **Confirmed interval enum** (from `smartapi-python` test fixtures +
  marketcalls.in walkthrough, cross-checked): `ONE_MINUTE`, `THREE_MINUTE`,
  `FIVE_MINUTE`, `TEN_MINUTE`, `FIFTEEN_MINUTE`, `THIRTY_MINUTE`, `ONE_HOUR`,
  `ONE_DAY`. No sub-minute (tick/second) interval exists. [A/B — matches
  research/81's existing note and per-interval day-window caps already
  recorded there: 1m ≤30d, 3m ≤60d, 5/10m ≤100d, 15/30m ≤200d, 1h ≤400d,
  1d ≤2000d, capped at 8,000 candles/request]
- **No historical open interest — confirmed directly by an Angel One
  moderator** on the official SmartAPI forum release note (topic 4012,
  "Release Note: Free Historical Data Access..."): *"This API does not
  provide Open Interest info for now"* (team said they'd announce if this
  changes). [A — official moderator statement, matches research/81's
  existing finding] Note: a separate angelone.in marketing article lists
  "open interest" among live Market Feed API quote fields — that is the
  **real-time quote/feed API**, a different endpoint from historical
  `getCandleData`; do not conflate the two. Also confirmed: expired
  F&O contracts have no historical data available (only currently active
  contracts).

## 6. Daily-expiry behavior of the jwtToken/session
Two distinct, non-conflicting facts, both corroborated by multiple
independent forum threads (search-snippet triangulated; SmartAPI's `/docs`
pages themselves render no static HTML so can't be WebFetched directly):
- The **`jwtToken` (access token) itself has a short validity window**
  (community/forum references cite ~2.5 hours), after which API calls using
  it return `AG8001 Invalid Token`.
- Within the same day, it can be **silently refreshed** via
  `generateToken(refreshToken)` (§3) without re-entering PIN/TOTP.
- The **overall session hard-expires at midnight** regardless of refreshes —
  "*the session established via SmartAPI remains active till 12 midnight,
  unless the user chooses to log out*." After midnight, `refreshToken` is
  also invalid and a fresh `generateSession(clientCode, pin, totp)` (new TOTP
  code) is required. **Practical implication for this project: the
  historical-adapter session builder must run `generateSession` fresh once
  per calendar day** (matches research/81's existing note "Session resets at
  midnight") — a stored TOTP secret makes this fully unattended/scriptable
  (no manual OTP entry), it just needs to run daily.

## 7. Exact credential list to supply (nothing else needed beyond what's below)
Already have: `api_key` (from the portal app), TOTP secret (the QR/base32
seed used with `pyotp.TOTP(secret).now()`).
**Still needed from the user, and sufficient once supplied — no other value
is required for a historical-data pull:**
1. **Client code** — Angel One trading account login ID.
2. **PIN / MPIN** — the account's trading-terminal login PIN.

With `{api_key, client_code, pin, totp_secret}` the adapter can:
`generateSession(client_code, pin, pyotp.TOTP(totp_secret).now())` →
`jwtToken` → `getCandleData(...)` for OHLCV bars, `ONE_MINUTE`…`ONE_DAY`, no
OI, run once daily before use (session resets at midnight).
